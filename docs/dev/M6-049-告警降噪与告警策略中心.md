# M6-049 告警降噪与告警策略中心（实现说明）

> 对应任务卡：`docs/pm/board/doing/M6-049-告警降噪与告警策略中心.md`
> 架构依据：`docs/架构设计文档-V1.md` §3.7、§13.4

## 1. 背景

M6-040 的报警中心把 ClickHouse 拦截记录直接当成报警：同一域名每小时新建一条、全部为 `warning`、铃铛统计所有 `status='open'`。StevenBlack 这类 broad 情报源每天命中量极大，几分钟就能把右上角未确认数刷到几百，真正的 ThreatFox/系统故障反而被淹没；用户确认后下一小时同一域名又会重新出现。

M6-049 的核心是把「记录」和「通知」解耦：

```
ClickHouse 命中记录
  → alert（报警档案：稳定指纹 / 分类 / 级别 / notify 快照 / 决策链）
    → alert_policy / alert_silence（是否进入通知层）
      → 铃铛（只查 open AND notify=true）
      → notification_channel（Webhook / 邮件 / IM，失败写 notification_delivery）
```

## 2. 后端设计

### 2.1 数据模型（迁移 `0054_alerting.sql`）

- `alert_policy`：`scope_type/scope_key` 唯一，作用域 `intel_source > blocklist > kind > component > source > global`；字段含 `severity`、`notify_mode`、`alert_class`、`group_by`、`max_per_hour`、`repeat_after_sec`、`resolve_after_sec`、`enabled`。
- `alert_silence`：`matchers jsonb` + `starts_at/ends_at/reason`。
- `notification_channel`：非敏感配置 JSON + `secret_file`（只存路径），`min_severity`、`quiet_hours`、`enabled`、`last_test_at/last_status`。
- `notification_delivery`：每次外部投递的结果（sent/failed、错误、尝试次数）。
- `alert` 新增列：`fingerprint`、`alert_class`、`notify`、`policy_id`、`group_key`、`window_start`、`notify_count`、`last_notified_at`、`suppressed_by`、`silence_id`、`decision`、`repeat_after_sec`、`resolve_after_sec`。
- 启动时 `EnsurePolicies` 以 `ON CONFLICT (scope_type, scope_key) DO NOTHING` 落默认策略，不覆盖用户修改。

### 2.2 策略解析（`internal/module/alerts/policy.go`）

1. 过滤 `enabled=false` 的策略，按输入匹配。
2. **global 只兜底**：存在更具体作用域时，global 不参与合成，避免全局 `notify` 覆盖 StevenBlack 的 `digest`。
3. 只保留最高特异度（`intel_source=5` … `source=1`）的策略集合；同集合内多源命中取最高 `severity`，任一 `notify` 则通知。
4. 护栏：系统健康类 `off` 强制改为 `notify`；critical 安全/健康事件不允许 `off`。
5. 静音窗口在策略之后匹配，命中则 `notify=false`，并写 `suppressedBy/silenceId`。

默认姿态：

| 作用域 | 级别 | 模式 | 聚合 |
|---|---|---|---|
| StevenBlack | info | digest | source |
| Spamhaus | warning | digest | domain |
| URLhaus / ThreatFox | critical | notify | domain |
| OpenPhish | warning | notify | domain |
| 系统健康（db/dns/dhcp/logstore） | critical | notify | none |
| 全局兜底 | warning | notify | domain，30 条/小时 |

### 2.3 稳定指纹与冷却（`repo.go` / `repo_mem.go`）

- DNS `dedup_key` 改为 `dns|<group>|<source>|<client>|<domain?>`，移除 `YYYYMMDDHH`；`window_start` 记录当前小时。
- `Upsert` 用 `GREATEST(alert.count, EXCLUDED.count)` 合并重复回扫；`first_seen/last_seen` 取并集。
- 已确认报警只有在 `repeat_after_sec` 到期或数量 ≥10 倍时才重新打开；`resolve_after_sec` 到期由 `AutoResolveDNS` 自动 resolved。
- 返回 `JustNotified`，供采集器只在真实通知时消耗限流预算与触发外部通道。

### 2.4 聚合、限流与抑制（`collector.go`）

- `CollectDNS` 先按策略的 `group_by` 聚合：`source`/`client` 聚合时清空 `domain`，标题改为「已拦截 N 次风险访问（来源）」并附 Top 域名；`domain` 保留单域名细节。
- 单源与全局每小时上限：`capExceeded` 只读检查，`consumeBudget` 在 `JustNotified=true` 后扣减，避免重复回扫把额度吃光；超限报警 `notify=false`，决策链标记 `capped=true`，并写「限流」原因。
- 系统健康报警不占用 DNS 通知预算，避免 broad 源洪水把数据库/ DNS 故障挤掉。
- 内置抑制：DNS 服务不可用时，上游探活失败自动归档。
- 通知钩子只依赖 `Notifier` 接口，采集器单测可用 fake 替换。

### 2.5 通知通道（`channel.go` / `repo_admin.go`）

- 支持 webhook/email/feishu/dingtalk/wecom/slack/teams。
- Webhook 带 `X-IPAM-Signature: sha256=<HMAC>`（密钥来自 0600 文件）；IM 使用各自文本消息结构；邮件走 SMTP（支持 PlainAuth、多收件人）。
- 通道级 `min_severity` 与 `quiet_hours` 过滤，critical 不受勿扰时段限制。
- 测试发送统一走 `TestChannel`，结果写回 `last_test_at/last_status`，并记录 `notification_delivery`。
- 删除/清除密钥时同步删除文件。
- 部署：`ipam-run` 卷持久化 `/run/ipam/notify-secrets`，`volume-init` 预创建并 chown 10001 / mode 0700；`IPAM_PUBLIC_URL` 决定通知里的站内外链基址。

### 2.6 API 与权限

新增 `/alerting/*`：总览、策略 CRUD + 模拟、静音 CRUD、通道 CRUD + 测试、投递记录。`/logs/alerts` 增加 `notify`、`alertClass` 过滤；`/logs/alerts/unread` 只统计 `notify=true`。

RBAC：`/api/v1/alerting` 归 `system` 域，页面查看 `system:read`、配置 `system:write`；报警确认仍走 `logs:read`。

## 3. 前端

- 新增 `views/system/alerting/index.vue`，6 个页签：总览 / 策略 / 聚合与抑制 / 静音 / 通知通道 / 变更审计。
  - 总览：记录、通知、归档、降噪率、critical 被抑制告警；记录/通知双趋势；来源降噪排行。
  - 策略：作用域、级别、模式、分类、聚合、上限、冷却；开关、编辑、删除（全局兜底不可删）；表单内可运行只读模拟。
  - 静音：多条件 matcher + 时间窗 + 理由，到期自动失效。
  - 通道：Webhook/邮件/IM 表单、密钥只写、测试发送、最近投递记录。
  - 审计：复用统一审计日志，检索 `alerting`。
- 报警中心（`views/logs/alerts/index.vue`）：
  - 默认「仅需关注」（`notify=true`），可切换「全部 / 归档」。
  - 标题与详情展示「归档」标记、通知层状态、决策链（命中策略、作用域、策略模式、最终处置、抑制原因、通知次数、窗口）。
- 情报源卡片（`views/dns/blocklist/intel-sources-card.vue`）展示该源当前告警模式标签；无 `system:read` 时静默跳过。
- 路由与 locale：`page.system.alerting`；`alerting.json`（zh/en）承载页面文案；`logs.json` 补充通知范围与决策链字段。

### 5.1 真实栈冒烟与缺陷修复（会话2）

真实栈（compose + PG + ClickHouse + 嵌入前端）冒烟时发现并修复两处问题：

1. **运行镜像滞后**：`/openapi.json` 中既无 `/alerting/*` 也无情报源 `runs/revisions`，说明容器仍是旧控制面。按「`pnpm run build:ipam` → `scripts/sync-webui.sh` → `go build`（`CGO_ENABLED=0`，嵌入新 dist）→ 基于现有镜像 COPY 新二进制的派生镜像 → `docker compose up -d --no-build control-plane`」更新，迁移 `0054/0055` 自动应用，接口与页面随之上线。
2. **告警页文案全为原始 key**（如 `alerting.title`）：本项目约定「文件名即第一段命名空间」，`langs/<locale>/alerting.json` 内容里又包了一层 `alerting`，运行时被合并成 `alerting.alerting.*`。移除该层包裹后恢复；`scripts/check-i18n-keys.py` 增加门禁：任何语言文件的顶层 key 与文件名同名即失败，防止复发。
3. **DNS 采集整轮失败**：日志出现 `can't scan into dest[35] (col: just_notified): cannot scan NULL into *bool`。`Upsert` 的 `RETURNING (last_notified_at = now())` 在新建 `notify=false` 告警时（`last_notified_at IS NULL`）返回 NULL。改为 `COALESCE(last_notified_at = now(), false)`，并新增 `repo_pg_test.go`（`IPAM_TEST_PG_DSN` 启用）覆盖「仅记录不通知 / 首次通知 / 重复扫描不重复通知」三种情况。

验证证据：`go test ./...`、`golangci-lint run ./...`（0 issues）、迁移在真实 PG 已应用；Playwright 登录后 6 个页签均渲染中文且无原始 key、策略表 15 行；采集日志恢复为 `[alerts] DNS 风险访问：合并 138 组`。

- `blocklist` 作用域已预留，当前事件未携带名单 key，暂不参与匹配。
- 通知投递暂为同步单次尝试，后续可增加退避重试与失败告警。
- `AckAll` 仍会确认全部 open 报警（含归档）；若需要“只确认通知层”，可改为 `WHERE notify=true`。
