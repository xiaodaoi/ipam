# M6-016 全链路压测与容量报告（实现说明）

> 日期：2026-11-01　环境：单机 12 vCPU / 7 GB，Docker Compose 全栈（control-plane + PostgreSQL 16 + ClickHouse 24.8 + Kea 4/6 + Unbound + Vector）
> 目的：给商业化交付一个可复现的「能扛多少」答案，并沉淀容量规划公式。

## 1. 工具与可复现性

### 1.1 API 压测（`tests/load/main.go`）

```bash
go run ./tests/load -base http://127.0.0.1:8443 -concurrency 10 -duration 20s -warmup 2s \
  -paths "/api/v1/dashboard,/api/v1/subnets,/api/v1/ledger?pageSize=50" \
  -out tests/load/artifacts/fullstack.json
```

- `-paths`：逗号分隔多路径，逐条压测并输出表格；
- `-warmup`：预热不采集，规避连接池/缓存冷启动；
- `-insecure`：自签 TLS 环境；
- `-out`：JSON 报告（RPS/p50/p95/p99/max/错误数）；
- 兼容旧用法 `-path`。

压测前需关闭通用限流（`IPAM_RATE_LIMIT=0`），否则 600 次/分钟/IP 会先触发 429。

### 1.2 ClickHouse 容量（`tests/load/capacity-ch.sh`，`make capacity-test`）

```bash
ROWS=5000000 bash tests/load/capacity-ch.sh   # 单日样本
ROWS=20000000 bash tests/load/capacity-ch.sh  # 4 天量
```

- 只创建/删除影子表 `ipam.logs_capacity`，结构与 `ipam.logs` 完全一致（含 TTL、索引），不触碰生产表；
- 样本比例 80% dns / 20% dhcp，2000 个客户端、5 万个域名，接近真实基数；
- 输出：写入耗时与行/秒、压缩/未压缩比、每行磁盘字节、典型查询耗时；结束时自动 DROP。

## 2. 全链路压测结果

10 并发 × 20s，每路径预热 2s，0 错误。

| 路径 | RPS | p50 | p95 | p99 | 说明 |
|---|---:|---:|---:|---:|---|
| `/api/v1/dashboard` | 8511 | 1.07ms | 1.84ms | 2.46ms | 命中 5s 快照缓存 |
| `/api/v1/subnets` | 3918 | 2.37ms | 3.75ms | 4.70ms | PG |
| `/api/v1/ledger?pageSize=50` | 727 | 13.31ms | 20.10ms | 23.97ms | PG 台账分页 |
| `/api/v1/dhcp/leases4` | 1290 | 7.25ms | 9.70ms | 24.15ms | 透传 Kea ctrl-agent |
| `/api/v1/dns/zones` | 7419 | 1.26ms | 2.04ms | 2.69ms | PG |
| `/api/v1/logs`（28h 窗口） | 117 | 84ms | 107ms | 118ms | CH，28 小时 ≈ 150 万行 |
| `/api/v1/logs/top`（7d） | 26 | 390ms | 446ms | 464ms | CH GROUP BY 客户端 |
| `/api/v1/logs`（7d 全窗口） | 14 | 709ms | 803ms | 1030ms | CH，7 天 ≈ 640 万行 |

结论：

- 控制面 + PG + Kea 的常规管理操作都在毫秒级，**单机支撑数十名管理员日常操作没有问题**；
- 瓶颈在 ClickHouse 日志检索：时间窗越大越慢，**默认时间窗应控制在 24 小时内**，7 天全窗口属于「应急排查」用法（14 RPS 仍可多人同时查，但不要当默认页）。

## 3. 压测发现的优化：仪表盘从 14 RPS → 8511 RPS

### 3.1 问题

优化前同一压测：`/api/v1/dashboard` **14.1 RPS，p50 692ms，p99 851ms**。

根因：`dashboard.Service.poolTop` 对每个地址池各发一次 ClickHouse `uniqExact` 查询。现网 17 个子网 / 16 个池 ⇒ 单次仪表盘请求 ~22 条 CH 查询（16 池 + 在线数 + 趋势 + 终端流 + QPS + 拦截量），全部串行；10 并发时把 CH 连接池（5 条）和扫描资源打满。

### 3.2 修复

1. **一次取集合**：新增 `logquery.Store.DistinctClientIPs`（`SELECT DISTINCT client_ip`），今日活动 IP 只查一次；
2. **内存侧池计数**：IP 解析为 `netip.Addr` 排序后，对每个池区间二分统计（`countAddrInRange`），复杂度 `O(n log n + p log n)`；
3. **并发取数**：在线数 / 小时趋势 / 终端流入流出 / DNS 指标 四路 `goroutine` 并行，任一失败只降级该指标；
4. **快照缓存**：结果按 `poolTopN` 缓存默认 5s（`IPAM_DASHBOARD_CACHE_TTL`，0=关闭），串行化刷新避免缓存击穿；前端本就 30s 轮询，缓存不损失可感知新鲜度。

效果：**8511 RPS / p50 1.07ms / p95 1.84ms**（约为原来的 600 倍），CH 查询数从 ~22 条/请求降到 5 条/5 秒。

### 3.3 语义变化

`OnlineNow` 口径由 `uniqExact(coalesce(toString(client_ip),''))` 改为「去重后的非空客户端 IP 数」。原口径在有 NULL IP 行时会把 `''` 也算作 1 个「在线终端」，属于旧实现的偏差；新口径与内存实现、页面语义一致。

## 4. ClickHouse 容量

### 4.1 写入与压缩（5,000,000 行单日样本）

| 项目 | 实测 |
|---|---|
| 写入耗时 | 5.561s（单连接单批 `INSERT … SELECT`） |
| 写入速率 | ≈ 899,000 行/秒 |
| 磁盘占用 | 111.40 MiB（含索引/标记） |
| 未压缩 | 683.52 MiB |
| 压缩比 | 6.22× |
| 每行磁盘 | 23.4 B（合成数据，字符串重复度高） |

### 4.2 真实数据口径（更保守，推荐用于容量规划）

现网开发库 `ipam.logs`：**23,967,071 行 / 1.02 GiB**（10 天数据，真实域名与 detail 文本）⇒ **≈ 44.6 B/行**。

据此推算：

| 日增量 | 每日磁盘 | 180 天（默认 TTL） | 365 天（在线） |
|---|---:|---:|---:|
| 100 万行 | 44.6 MB | 8.0 GB | 16.3 GB |
| 300 万行 | 134 MB | 24.1 GB | 48.9 GB |
| **500 万行** | **223 MB** | **40.1 GB** | **81.4 GB** |
| 1000 万行 | 446 MB | 80.2 GB | 162.8 GB |

> 磁盘规划建议：在在线数据之外预留 ≥2 倍空间（合并临时文件、Parquet 归档、PG 备份、镜像），即 500 万行/天 + 180 天 TTL ⇒ 在线约 40GB、整机建议 ≥150GB。

### 4.3 查询延迟（500 万行/天，单次）

| 查询 | 耗时 |
|---|---:|
| 全天 `count()`（type=dns） | 55ms |
| 首页 50 行（全列 + 三元组倒序） | 44ms |
| 域名子串检索（全天） | 68ms |
| 客户端 Top10（24h，dhcp） | 45ms |

在真实 2400 万行表上：7 天 `count()` 约 39ms、首页 50 行约 29ms，说明 **单日 500 万行时查询预算（`max_execution_time=3s`）有 40 倍以上余量**。

### 4.4 边界

- 7 天全窗口分页：需要跨 35 个 part、扫描 640 万行，10 并发下 14 RPS / p50 709ms。属预期行为，非缺陷；通过「默认 24h 时间窗 + 缩小范围/加 type/domain 过滤 + CSV 导出」规避；
- 深分页上限 1 万条（M6-015）继续生效；
- ClickHouse 侧 part 数会随 Vector 写入增长，`IpamLogPartsHigh > 500` 告警仍是对的第一道防线。
