# M6-040 应用内报警中心实施说明

## 1. 目标与边界

在日志中心新增「报警日志」，把两类事件统一到一个可查询、可统计、可确认的视图：

1. **风险域名访问**（DNS 拦截）：回答「哪些客户端地址访问了哪个被拦截域名、访问了多少次」；
2. **系统故障**：数据库/日志存储/DHCP/DNS 掉线、磁盘水位、日志外发降级、情报源同步失败、上游探活失败。

右上角报警栏轮询未确认报警；**查看即确认**（点击通知或报警行），确认是全局的（单机产品），
记录 `acked_by`。系统故障恢复后自动置为 `resolved`，再次发生重新打开为未确认。

不在本期范围：邮件/Webhook/钉钉外发（沿用 M6-005 告警通道）、按用户维度的已读状态、
原始日志明细二次存储。

## 2. 数据模型

迁移：`db/postgresql/migrations/0047_alert.sql`。

| 字段 | 说明 |
|---|---|
| `dedup_key` | 唯一键，决定聚合粒度 |
| `source` | `dns` / `system` |
| `kind` | `risk_url`、`db_down`、`logstore_down`、`dhcp_down`、`dns_down`、`disk_pressure`、`log_export_degraded`、`intel_sync_failed`、`upstream_probe_failed` |
| `severity` | `critical` / `warning` / `info` |
| `status` | `open`（未确认）/ `acked`（已确认）/ `resolved`（已恢复） |
| `client_ip` / `client_mac` / `domain` | 风险访问维度 |
| `component` | 系统故障组件中性名（database/logstore/dhcp/dns/host/log-export/intel/upstream） |
| `count` | 窗口内事件数或连续故障次数 |
| `first_seen` / `last_seen` | 首末发生时间 |
| `acked_at` / `acked_by` / `resolved_at` | 确认与恢复留痕 |

### 去重键

- DNS：`dns|<client_ip>|<domain>|<YYYYMMDDHH>` —— **1 小时桶**，同小时累加，跨小时新开一条。
- 系统：`system|<kind>|<component>` —— 同一组件只有一条活动报警。
- 磁盘：`system|disk_pressure|<mount>`；情报源：`system|intel_sync_failed|<source key>`；
  上游：`system|upstream_probe_failed|<upstream id>`。

### 合并语义（`ON CONFLICT`）

- `count = GREATEST(alert.count, EXCLUDED.count)`：采集器 60s 回扫最近 2 小时，
  ClickHouse 返回的是「桶内累计值」，重复回扫不会重复计数；
- `first_seen = LEAST(...)`、`last_seen = GREATEST(...)`；
- 之前已 `resolved` 的同键事件：状态回到 `open`，清除 `acked_at/acked_by/resolved_at`，
  `count` 用本次值（视为新一次故障/新一小时的访问）。

> 注意：DNS 报警在同一小时内被确认后，继续命中**不会**重新变未确认（避免同一事件反复打扰）；
> 下一个小时桶会产生新的报警。系统故障恢复后再次发生则重新打开。

## 3. 采集

`internal/module/alerts/collector.go`，每 60s 一轮，启动即执行一次。

### 3.1 DNS 风险访问

`internal/module/logquery/alerts.go` 新增 `(*ChStore).BlockedEvents`：

```sql
SELECT toStartOfHour(ts), coalesce(toString(sip),''), domain, any(category),
       count(), min(ts), max(ts)
FROM ipam.logs
WHERE ts >= ? AND type='dns' AND action='blocked' AND domain != '' AND sip IS NOT NULL
GROUP BY 1,2,3
ORDER BY count() DESC
LIMIT 5000
```

- `sip` 是 DNS 查询源地址（客户端），`action='blocked'` 由 Vector 的 `parse_rpz` 打标；
- 单次最多 5000 组，极端场景按命中次数截断，避免控制面内存被打满；
- 内存模式（未配置 `IPAM_CH_ADDR`）不启用 DNS 报警采集。

### 3.2 系统故障

| 探针 | 判据 | 级别 | 阈值 |
|---|---|---|---|
| 数据库 | `pool.Ping` 失败 | critical | 连续 2 次 |
| 日志存储 | ClickHouse `Ping` 失败 | critical | 连续 2 次 |
| DHCP | Kea `version-get` 失败 | critical | 连续 2 次 |
| DNS | `/run/ipam/unbound-ctl.sock` 不可达 | critical | 连续 2 次 |
| 磁盘 | 任一挂载点 ≥90% | warning | 立即 |
| 日志外发 | `exportSvc.Status().Degraded` | warning | 立即 |
| 情报源 | 已启用且 `lastStatus=failed` | warning | 立即 |
| 上游 | 已启用且 `ConsecutiveFails >= 3` | warning | 立即 |

- 服务探针连续失败 2 次才报警，避免网络抖动误报；失败但未达阈值也计入「当前故障集合」，
  不会被误判为已恢复。
- `ResolveStaleSystem(managedKinds, activeKeys)` 只恢复**本轮已启用探针**产生的报警：
  未配置的能力（如未接 ClickHouse）不会把历史报警错误地置为 resolved。

## 7. 踩坑与约束

- **不要按 `last_seen` 直接累加计数**：采集器回扫会重复。必须用 ClickHouse 桶内累计值 +
  `GREATEST` 合并。
- **未配置的探针不能参与自动恢复**：否则未接 ClickHouse 的环境会把历史 `logstore_down`
  错误地标成已恢复。用 `managedKinds` 限定。
- **系统探针需要连续失败阈值**：单次抖动不应产生报警；但失败未达阈值时要保留在故障集合中。
- **界面不出现底层产品名**：组件名统一用中性词（数据库/日志存储/DHCP/DNS/主机…）。
- **确认动作降级为 `logs:read`** 只对 `/logs/alerts/ack*` 生效；其他 logs 写操作仍走 `logs:write`。

## 9. 情报来源归属与模糊查询（2026-11-20 增强）

### 9.1 目标

报警记录不仅要知道「哪个域名被拦截」，还要知道「是哪个外部情报源拦下的」；
列表、统计与右上角报警栏都要展示来源，并支持按来源模糊查询。

### 9.2 数据模型

迁移 `db/postgresql/migrations/0048_alert_intel_source.sql` 新增两列（默认空串，兼容历史行）：

| 列 | 含义 |
|---|---|
| `intel_source` | 命中的情报源 key（多个用英文逗号分隔），用于稳定过滤/审计 |
| `intel_source_name` | 命中情报源的显示名（多个逗号分隔），历史留痕：源改名/删除后仍可读 |

非外部情报源命中（自定义封禁、内置规则）保持空串，前端按 `detail` 中的 RPZ category
（`intel.custom.rpz` / `intel.hot.rpz` / `intel.broad.rpz`）展示中性文案。

### 9.3 归属算法

`internal/module/dns/intel_attrib.go`：

- 懒构建「域名 → 源」内存索引：读取所有**已启用**源的域名缓存（`<rpz dir>/sources/<key>.domains`），
  不把百万级 IOC 入库；
- 查询按后缀由长到短匹配：先精确域名，再逐级去掉最左标签，取最具体的一层；
  同一层被多个源收录时全部返回（按 key 排序，输出稳定）；
- 源新增/编辑/启停/同步/删除后调用 `invalidateAttribution()`，下次查询自动重建；
- 采集器通过 `DomainAttributor` 接口注入（`main.go: alertCol.SetAttributor(intelSvc)`），
  DNS 事件写入来源字段；自定义封禁/内置规则无来源时为空。

> 归因是「尽力而为」：日志只记录域名被拦截，无法反推 unbound 最终命中的具体记录；
> 后缀匹配保证子域（如 `j8.asdlot.org`）能归到源中的 `asdlot.org`。

### 9.7 为什么当前报警来源几乎全是 StevenBlack/hosts

这是当前**流量结构**决定的，不是归属算法只认一个源：

- 真实栈同时启用了 3 个源：ThreatFox（hot，28,492 条）、OpenPhish（hot，281 条）、
  StevenBlack/hosts（broad，73,070 条）；
- 报警采集窗口为最近 2 小时；当时 767 条 DNS 报警涉及 61 个唯一域名，
  这 61 个域名**全部**存在于 StevenBlack 缓存，ThreatFox/OpenPhish 命中 0 个；
- 近期被拦截的域名集中在广告/统计/遥测（`h-adashx.ut.taobao.com`、`tdid.m.qq.com`、
  `hm.baidu.com`、`beacons.gvt2.com`、`sb.scorecardresearch.com` 等），属于 broad 层，
  正好由 StevenBlack 覆盖；
- ThreatFox 缓存中确实有 `j8.asdlot.org`、`g.gp108.org`，但它们是 2026-11-19 10:02
  的 `dig` 验证流量，早于 2 小时回扫窗口，因此不会生成报警。

换言之：只有当客户端真正访问到 hot 层 IOC 时，来源才会出现 ThreatFox/OpenPhish；
若一个域名同时被多个源收录，归属会按 key 排序返回多个来源。

### 9.8 已加白域名仍显示「拦截」：根因与修复（2026-11-20）

**现象**：白名单里有 `*.crpower.com.cn`，报警中心仍出现「风险域名 `*.crpower.com.cn`」，
看起来像加白失效；客户为避免影响业务删除了白名单。

**核查结论：DNS 实际没有被拦截，是日志/报警误报。**

- unbound 日志里该域名的命中行是白名单放行：

  ```
  rpz: applied [wl.whitelist.rpz] *.crpower.com.cn. rpz-passthru 2406:...@51578 ueszk.crpower.com.cn. AAAA IN
  ```

  `rpz-passthru` 表示继续正常解析，不是 `rpz-nxdomain` 拦截；
- ClickHouse 中该域名同期有 439 条 `resolve/NOERROR`，说明客户端拿到了正常应答；
- 该域名不在任何情报源/自定义封禁区里，唯一来源就是白名单区的放行日志。

**根因**（`config/vector/vector.toml` 的 `parse_rpz`）：

1. 只匹配 `rpz: applied` 就写 `action=blocked`，没有区分 `rpz-passthru`（放行）；
2. 取的是 `[zone]` 后的第一个 token，即**命中的规则名**。白名单以 `*.crpower.com.cn`
   通配规则命中，于是把规则名当成了查询域名入库。

两者叠加，报警中心就出现「白名单域名被拦截」的假报警，同时把仪表盘「今日拦截量」抬高
（本次真实栈累计 88,136 条假拦截：`*.crpower.com.cn` 63,864、`*.crc.com.cn` 24,257、
`*.baidu.com` 15）。

**修复**：

| 位置 | 改动 |
|---|---|
| `config/vector/vector.toml` | `parse_rpz` 跳过 `rpz-passthru`；域名优先取 `client@port` 之后的真实查询名，并补齐 qtype |
| `internal/module/logquery/alerts.go` | 报警聚合 SQL 排除含 `*` 的域名（兜底旧数据/其他解析路径） |
| `internal/module/alerts/collector.go` | 采集循环跳过通配规则名，配套单测 `TestDNS通配规则名不生成报警` |
| `db/postgresql/migrations/0049_alert_drop_wildcard_domain.sql` | 清理历史假报警（`source='dns' AND domain LIKE '%*%'`） |

**数据修复（真实栈）**：

- `ALTER TABLE ipam.logs DELETE WHERE type='dns' AND action='blocked' AND position(domain,'*')>0`
  删除 88,136 条假拦截（mutation 已执行完成）；
- 迁移 0049 删除 462 条历史假报警；
- Vector 校验：`vector validate` 通过；用 `vector vrl` 对真实日志行验证——`rpz-nxdomain`
  产出 `domain=sdk.e.qq.com`，`rpz-passthru` 被 `abort`；
- 修复后 3 分钟内新入库拦截记录的域名均为真实查询名，通配名 0 条。

**建议**：`crpower.com.cn` 不在任何情报源中，可安全重新加入白名单；白名单只影响
RPZ 判定，不会改变正常解析。
