# M6-032 主机资源指标落库与历史查询：实现说明

## 1. 背景与目标

仪表盘和「服务与运行」页原有主机资源卡片是**即时采集**：打开页面才读一次 `/proc`，读不到就空着，重启即丢。客户问「昨晚 2 点是不是 CPU 打满 / 磁盘是不是备份写满」时无据可查。

本任务把指标按分钟落库，并提供历史序列与峰值汇总，同时修掉一个既有的采集缺陷。

### 1.1 先修的前置缺陷：多写者污染 CPU 差值

`hostmetrics.Collector` 的 CPU 使用率来自两次 `/proc/stat` 读数的差值，而它原先被**三处并发调用**：

| 调用方 | 频率 |
|---|---|
| `GET /system/metrics`（页面轮询） | 每个打开页面 10s |
| `/metrics`（Prometheus 抓取） | 15s |
| `logexport.Watermark`（磁盘水位降级判断） | 1min |

三个调用者共享 `prevTotal/prevIdle`，等于「任意两个调用者之间的间隙」被当成采样窗口，CPU 数值本身不可解释。落库前必须先收敛为**单写者**，否则历史数据只是把噪声固化下来。

## 2. 设计决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 存储介质 | PostgreSQL（同库） | 离线单机部署必带 PG；已有 `subnet_utilization` 同款范式；数据量极小；join 审计方便 |
| 不选 ClickHouse | — | 为指标再引一套 DDL/迁移/备份路径；CH 故障时指标缺失；会模糊「日志归档」边界 |
| 不选仅 Prometheus | — | 客户现场不一定装 Grafana；装了也不能在管理页直接看 |
| 采样间隔 | 60s | 30 天 ≈ 43k 行 / 10MB；比现有利用率采样（4.9k 行/天）还少 |
| 保留 | 30 天，可配 | 定位「昨晚」类问题足够；不做小时级 rollup（避免第二处不一致来源） |
| 降采样 | 查询侧 `date_bin()` | 不做预聚合表；PG 16 原生支持 |
| 节点维度 | `node` 列默认 `local` | 为 M6-003B 双机主备预留，避免届时改表 |
| 备份 | 排除数据行 | 指标无业务价值；换机恢复后旧机器历史会误导排障 |

## 3. 数据流

```
/proc (宿主只读挂载)
   └─ hostmetrics.Collector.Sample()        ← 单写者，5s（IPAM_HOST_SAMPLE_INTERVAL）
        └─ Snapshot()  (atomic pointer)
             ├─ GET /system/metrics          ← 页面实时卡片（10s 轮询）
             ├─ /metrics  ipam_host_*        ← Prometheus 抓取
             ├─ logexport.Watermark          ← 磁盘水位降级
             └─ systemmetric.Service.Sample()← 60s，落 PG（system_metric + 子表）
                    ├─ GET /system/metrics/history  (date_bin 降采样)
                    └─ GET /system/metrics/summary  (窗口峰值)
```

控制面指标（goroutine、堆、连接池、日志新鲜度）与宿主指标**同一行**写入，保证时间轴对齐——排查「页面卡」时能直接看出是 CPU、内存还是连接池/日志积压。

## 5. 采样语义（易错点）

| 点 | 处理 |
|---|---|
| 首个样本 CPU 恒为 0 | `Collector.Valid()` 为 false 时 `Service.Sample` 直接跳过，不写脏样本 |
| 采样时刻漂移 | `time.Now().UTC().Truncate(interval)`，整分钟对齐 |
| 重启/重复写 | `UNIQUE(node, ts)` + `ON CONFLICT DO NOTHING`；冲突时子表也不再写 |
| DB 短暂不可用 | 跳过本轮 + `log.Printf`，**不攒队列**（避免内存膨胀） |
| 清理放大 | Prune 每小时最多一次，不是每分钟 DELETE |
| 挂载点增删 | 明细进子表，主表只存 `disk_root_pct` / `disk_max_pct` / `disk_worst_mount` |
| 子表膨胀 | `ON DELETE CASCADE` 随 Prune 一并回收 |

## 6. API 契约

| 端点 | 说明 |
|---|---|
| `GET /system/metrics` | 不变（实时快照），改为读缓存，避免每次请求触发磁盘 IO |
| `GET /system/metrics/history?from&to&step` | 时间桶均值（CPU/内存/负载/磁盘），磁盘取桶内最大值；返回点 ≤720，窗口 ≤90 天，超限 400 |
| `GET /system/metrics/summary?hours` | 峰值/均值/峰值时刻/最满挂载点/`since`（历史起始） |

权限沿用现有 `dash:read`（`/api/v1/system/metrics*` 前缀归 `dash` 域），未新增权限点。

响应头 `X-Metric-Window-From` / `X-Metric-Window-Step` 回带服务端实际窗口与粒度（前端可提示「已自动降采样」）。

## 7. 容量

| 项 | 数值 |

| 行数/天 | 1440（60s） |

## 9. 边界与后续

- **不做**：进程级 top、每网卡流量、实时流式指标、多机采集（等 M6-003B 用 `node` 列）。
- 恢复备份会按 `--clean` 重建指标表 → **历史指标在恢复后清空**（可接受：恢复本身是灾难操作，且避免跨机器污染）。
- 二期（M6-034 候选）：阈值事件化（连续 3 次超限记一条 `system_metric_event`）+ 在趋势图上叠加备份/恢复/重启审计时刻。
- `/metrics` 仍只暴露百分比，不暴露挂载点路径（目录名可能含客户信息）；路径仅管理页可见。
