# M6-014 日志查询性能与重复入库修复

## 1. 事故链

```
Vector 重建（M6-008）
  → /var/lib/vector 未持久化，checkpoint 丢失
  → file source read_from=beginning 重新读取整份日志
  → parse_unbound/parse_dns_log 使用 now() 作为 ts
  → 历史日志全部落在当前时间，44M 行洪峰
  → logs 表 ORDER BY (type, client_mac, ts)，ts 过滤全表扫描
  → count + ORDER BY 超过 max_execution_time=3s
  → handler 统一返回 CH_DOWN "日志存储暂不可达"
```

## 2. 采集修复

- compose：

```yaml
volumes:
  - vector-config:/etc/vector
  - vector-data:/var/lib/vector
```

- `config/vector/vector.toml`：
  - `read_from = "end"`；
  - `parse_unbound`：`.timestamp = from_unix_timestamp!(to_int!(m.ts), unit: "seconds")`
  - `parse_dns_log`：`.timestamp = from_unix_timestamp!(to_int!(parsed.ts), unit: "seconds")`

已用 `vector validate` 和 VRL CLI 对真实日志行验证。

## 3. 表重建

目标结构：

```sql
ENGINE = MergeTree
PARTITION BY toDate(ts)
ORDER BY (ts, client_mac, domain)
TTL toDateTime(ts) + INTERVAL 180 DAY DELETE
```

与查询 `ORDER BY ts DESC, client_mac DESC, domain DESC` 和游标 `(ts,client_mac,domain)` 完全一致。

执行步骤：

1. 创建 `logs_v2`；
2. `INSERT INTO logs_v2 SELECT * FROM logs`（清理事故时排除重放窗口）；
3. 校验行数/时间范围；
4. `RENAME TABLE logs TO logs_old, logs_v2 TO logs`；
5. 补拷切换窗口尾部数据；
6. `TRUNCATE logs_topn_hourly` 并从新表重建；
7. 确认后 `DROP TABLE logs_old`。

本次线上清理窗口：

- `2026-10-29 07:35:00`–`07:49:00`
- `2026-10-30 02:52:00`–`03:06:30`

## 4. 错误语义

`writeLogErr`：

- 超时关键字（Timeout exceeded / max_execution_time / timeout）→ `QUERY_TIMEOUT`；
- 其他 → 记录 `[logs] 查询失败: ...`，返回 `CH_DOWN`。

避免把“查询太慢”误报为“存储宕机”，同时保留服务端根因日志。

## 5. 验证数据

- 6h：34ms；24h：135ms；30d：0.93s；
- 行数 67.3M → 23.0M，磁盘 2.72GiB → 约 1.0GiB；
- Vector 重启后 20s 增量 895 行，无重放；
- Top 30d 0.73s，QPS 30d 0.11s；
- E2E 11/11。

## 6. 运维注意

- 不要把 `read_from` 改回 `beginning` 除非明确要回填，并在回填后改回 `end`；
- 重建脚本需维护窗口与约 1.2 倍表空间；
- `logs_old` 确认后再删除；
- 事故窗口内的正常日志如需补齐，可从 Kea/Unbound 原始日志文件重新导入。
