## 1. 背景与问题

改造前 `forward-zone "."` 只取 `created_at` 最早的第一个 enabled 上游（`cmd/control-plane/conf_apply.go`、`internal/engine/unbound/forward.go` 各有一份相同逻辑）。真实环境里最早一条是测试数据 `e2e-fix验证`（`114.114.114.114`），导致：

- 其余 12 条已启用公网上游对默认解析完全不生效；
- 单条默认上游故障时，未命中缓存（含过期缓存）的公网域名直接 `SERVFAIL`；
- 上游页「权重越高被选中概率越大」与实际不符——`weight` 未参与任何选路；
- 条件转发规则 UI 只能选一个上游，多上游只能靠 API 写入。

## 2. 设计

### 2.1 默认公网出口池

- `upstream` 表新增 `is_default boolean NOT NULL DEFAULT false`（迁移 `0050_upstream_default.sql`）。
- 选择规则统一收敛到 `dns.DefaultForwardUpstreams`：
  1. 取所有 `Enabled && IsDefault` 的上游；
  2. 一个都没有时，回退第一条 `Enabled`（兼容旧部署，行为与改造前一致）；
  3. 与 `created_at` 顺序无关，但列表仓储仍按 `created_at` 排序，便于人工识别。
- 所有默认上游的地址去重后写入同一个 `forward-zone "."`；unbound 按 infra-cache RTT 自行选路、超时换地址、15 分钟重新探测。
- `"."` 仍只允许公网地址：标记默认时逐地址校验，拒绝 RFC1918、环回、链路本地、ULA、CGNAT、文档/基准等保留段。内网 DNS 只能通过条件转发规则使用。
- 条件转发规则中的 `"."` 不再参与下发（默认池独占该 zone），避免重复 `forward-zone` 触发 `unbound-checkconf` 拒绝。

### 2.2 条件转发多上游

- API 契约本来就支持 `upstreamIds: []`，本次只改前端：规则表单改为多选，创建/更新直接提交所选集合。
- 服务端沿用既有逻辑：规则引用的每个 enabled 上游，其全部地址写入同一 `forward-zone`，仍由 unbound 按 RTT 选路。

### 2.3 文案校正

- 上游列表/表单明确「权重（预留）」，提示「当前不参与选路，unbound 按上游 RTT 自动选择地址」。
- 健康状态文案保持「仅供排障参考」，与 M6-036 的实现一致。

## 6. 边界与后续

- unbound 自身会按 RTT 在默认池内选路；控制面 prober 的健康状态仍只用于展示/报警，不做主动摘除（见 M6-036）。
- 默认池中的 DoT 上游在静态渲染中按「同区只取 DoT」处理；动态 `forward_add` 通道不携带 TLS 参数，最终以渲染文件 + reload 为准。
- 若未来要做「按健康摘除/回切」，需先补 ADR 并同时调整 `SyncForward`/`SyncForwardRules`，避免与控制面、unbound 两套重试机制冲突。

## 7. M6-042 收口（2026-11-22）

复核发现三个边界问题并已修复：

1. **显式默认全部停用时曾回落非默认上游**：原实现只要「没有 enabled+isDefault」就回退第一条 enabled，若此时还有内网上游启用，会把内网 DNS 带回 `.`。现改为：只要存在任何 `is_default` 标记，就只使用 enabled 的默认上游；全部停用时返回空集，不回落。从未标记默认的旧部署仍保持回退行为。
2. **界面无法区分默认池状态**：上游页新增提示——未标记默认时提示兼容回退；标记但全部停用时明确告警 `.` 不再转发；停用的默认条目显示「默认出口（已停用）」。
3. **`.` 规则会“保存成功但不生效”**：条件转发规则创建（含 dryRun）在服务端拒绝 `.` 并返回 `400 DEFAULT_RULE_MANAGED`；前端同步拦截并提示到上游页配置。spec 已先行说明。

真实栈验证：停用唯一默认上游后，渲染文件与 `list_forwards` 均无 `.`，且未回落到内网；重新启用后 `.` 恢复三地址。
