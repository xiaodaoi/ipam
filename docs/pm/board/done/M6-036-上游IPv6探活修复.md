## 问题与根因

**现象**：上游列表所有 IPv6 条目（`upstream-v6-136`、`upstream-v6-137`、`ipv6`）均为 `up=false`、`rttMs=0`、`consecutiveFails=63473`；IPv4 条目全部正常。

**已确认事实**：

1. 数据库里两条 IPv6 上游地址完好，未被删除：`[2406:440:3c08:101:0:1:0:136]:53`、`[...:137]:53`；
2. `unbound-control list_forwards` 中没有这两条（它们未挂到任何转发规则），unbound 实际解析用的是 IPv4 上游；
3. 探活从 **control-plane 容器**发起，该容器在默认桥接网络，只有 IPv4：`/proc/net/if_inet6` 仅 `lo`，访问任何 IPv6 立即 `Network is unreachable`；
4. 从宿主/ unbound（hostNetwork）实测：`2406:...:136`、`2406:...:137`、`2400:3200::1` 的 UDP/TCP 53 均返回 NOERROR，**三者实际都健康**；
5. 失败计数无上限，15s 一次 × 11 天 = 63473，说明容器自上次重建后一直在累计；
6. `SyncForward` / `SyncForwardRules` 只按 `enabled` 过滤，**不读取健康状态**，所以「已摘除」只是标签，未真正摘除任何地址；界面提示「摘除中的上游不参与递归选路」与实现不符。

**根因**：控制面容器无 IPv6 出口 → 所有 IPv6 上游被误判为 down；加上探活只取 `Addrs[0]`、失败计数无上限、文案把「探活失败」写成「已摘除」，放大了误解。

## 目标

- 让 control-plane 具备 IPv6 出口，IPv6 上游能被真实探测；
- 一个上游有多个地址时，任一地址可达即视为在线（RTT 取最小值）；
- 失败计数封顶，避免出现 6 万+ 的无意义数字；
- 把「已摘除」改为「探活失败」，并明确健康状态仅用于排障展示，不改变转发选路；
- 探活不长时间持锁，避免上游列表接口被 2s 超时拖慢。

## 方案

| 项 | 决策 |
|---|---|
| IPv6 出口 | compose 为 control-plane 增加 IPv6-only 网络 `probe-v6`（`enable_ipv6: true`，默认 `fd00:1:2:3::/64`，可用 `IPAM_PROBE_V6_SUBNET` 覆盖）；数据面 unbound/kea 仍为 hostNetwork，不受影响 |
| 多地址探测 | 遍历 `u.Addrs`，任一成功即 up；RTT 取成功地址中的最小值 |
| 失败计数 | 封顶 `999`（`maxConsecutiveFails`），避免无限增长 |
| 恢复语义 | 一次成功即恢复（原注释「2 连胜回切」与实现不符，一并修正） |
| 锁粒度 | 先无锁完成网络探测，再持锁更新状态；`Status` 不再被探测超时阻塞 |
| 文案 | `dns.upstream.health.down` / `summary.down` / `stat.abnormalHint` / `dns.common.removedSuffix` / 转发页 `linkedHint` 由「已摘除」改为「探活失败」；hint 改为「健康状态仅供排障参考，转发按已启用上游下发」 |
| API 契约 | 仅更新 description（不新增字段）；先改 `api/openapi` 再 `gen-openapi.sh` |
