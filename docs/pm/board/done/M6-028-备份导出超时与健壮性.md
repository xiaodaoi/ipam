## 问题（实测）

手动备份（`POST /api/v1/system/backups`）返回 202 后在 `clickhouse export 2026-10` 失败：

```
clickhouse export 2026-10: ch http export: Post "http://clickhouse:8123/?database=ipam&max_execution_time=600":
context deadline exceeded (Client.Timeout exceeded while awaiting headers)
```

ClickHouse `system.query_log` 显示同一查询的耗时波动很大：

| 时间 | 结果 | 耗时 | 说明 |
|---|---|---|---|
| 03:10 | QueryFinish | 142.9s | 系统空闲，成功 |
| 05:35–05:47 | Exception 159 | 746s | 并发负载（E2E + 写入）下超过服务端 `max_execution_time=600` |
| 06:05 | QueryFinish | 251.4s | 修复后正式备份成功 |

根因（三层硬编码且互相矛盾）：

1. `internal/module/logmanager/ch_admin.go:22` `chExportClient.Timeout = 5 * time.Minute`；
2. 同文件 URL 里 `max_execution_time=600`（10 分钟）> 客户端 5 分钟 → 客户端先放弃，
   服务端仍在跑（日志 746s），错误只暴露客户端超时；
3. `internal/module/backup/backup.go:133` 备份总预算固定 30 分钟。

**实测中又发现一个更严重的数据完整性问题**：把导出预算临时调成 40s 时，ClickHouse 在
`max_execution_time` 到点后**已发送 200 响应头**，随后把异常文本追加到响应体末尾；
旧代码只判断状态码，于是把「24MB 半截 Parquet + `Code: 159` 文本」记成 **success**
（正常同月文件 504MB）。这类备份恢复时必然失败，且不会被任何现有校验发现。

附带健壮性问题：

- 失败时**不清理半成品目录**（实测残留 51MB）；
- `execute` 的 `fail()` 用已取消的 `ctx` 写库，超时时记录可能永远停在 `running`；
- `httpQuery`（`Reset`/`RestoreMonth`）用 `http.DefaultClient`（无超时），对端挂死会泄漏 goroutine。

## 方案与实现

| 文件 | 变更 |
|---|---|
| `internal/module/logmanager/ch_admin.go` | ① 新增 `DefaultExportTimeout=30m`、`ChConfig.ExportTimeout`；② 去掉 `http.Client.Timeout` 固定值，改由每次请求的 context 控制预算，保留连接级超时；③ `max_execution_time` 由预算推导（客户端预算 −30s），保证先返回 ClickHouse 的明确错误；④ 抽出 `exportRange` 便于单测；⑤ 新增 `checkParquetComplete` 校验文件尾 `PAR1`，并回读尾部 `Code:` 文本作为诊断；⑥ 失败删除半成品文件；⑦ `httpQuery` 改用同一 client 并加请求预算 |
| `internal/module/backup/backup.go` | ① 新增 `DefaultTimeout=2h` 与 `SetTimeout()`；② `execute` 用可配置总预算；③ `fail()` 删除半成品目录、`sizeBytes` 置 0；④ `fail()` 用独立 10s context 落库，避免卡 `running` |
| `cmd/control-plane/main.go` | 解析 `IPAM_CH_EXPORT_TIMEOUT`、`IPAM_BACKUP_TIMEOUT`，非法值告警并回退默认 |

## 实施记录

### 2026-11-04

**定位**

- 从 `system.query_log` 确认 05:35 的 `SELECT * ... FORMAT Parquet` 运行 746s 后 `Exception 159`，
  而 03:10 同样查询 142.9s 成功 → 不是固定「大月份必然超时」，而是固定 5 分钟客户端预算在负载下误杀。
- 用 `IPAM_CH_EXPORT_TIMEOUT=40s` 复现时发现 200 + 半截文件仍被记 success，追加完整性校验。

**关键设计**

1. **预算单一来源**：`ExportTimeout` 同时决定客户端 context 与服务端 `max_execution_time`；
   服务端少 30s，让「ClickHouse 主动超时」优先于「客户端放弃」。
2. **HTTP 200 不代表成功**：ClickHouse 流式响应中途出错不改状态码，必须校验 Parquet 结束标记。
3. **失败必须可观测且可重试**：删除半成品 + 独立 context 落库，避免 `running` 僵尸记录与磁盘浪费。

**验证证据**

| 场景 | 结果 |
|---|---|
| 正常备份（默认预算） | `success`，`623,615,501` 字节，`2026-08/09/10/11` 四个月；Parquet 尾部均 `PAR1` |
| 备份可读性 | `logs-2026-08.parquet` 读回 `3932` 行 == 库内该月行数 |
| `IPAM_CH_EXPORT_TIMEOUT=2s` | `failed`，`日志导出 2026-09 超时（预算 2s）… 调大 IPAM_CH_EXPORT_TIMEOUT`，目录已删 |
| `IPAM_CH_EXPORT_TIMEOUT=35s` | `failed`，`ch http export status 408: Code: 159 … maximum: 5`，目录已删 |
| 清理无效备份 | 删除被旧代码误记为 success 的截断备份（204）；另删除一次失败残留 |

## 遗留与边界

- **恢复演练**（`POST /system/backups/{id}/restore`）仍需维护窗口，本次只验证到「备份成功 + Parquet 可读回」；
- 每次备份全量重导所有月份，单月日志很大时备份窗口与磁盘占用线性增长；增量/异地复制另立任务卡；
- Parsed 完整性只校验结束标记与尾部异常文本，不做逐行 checksum 对比；如需更强保障，可在后续增加 footer `num_rows` 与源表计数比对。
