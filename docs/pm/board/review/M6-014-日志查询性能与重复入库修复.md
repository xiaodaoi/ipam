## 现象

- 日志中心选「近 6 小时」查询很慢，最终提示 **“日志存储暂不可达”**；
- 近 24 小时直接 503（control-plane 3s 查询预算超时）；
- 相比 10 月 10 日前明显变慢。

## 根因

1. **Vector checkpoint 未持久化**：compose 未挂载 `/var/lib/vector`，M6-008 重建 Vector 后 checkpoint 丢失；
2. **file source `read_from = "beginning"`**：checkpoint 丢失后整份 unbound/kea 日志被重放；
3. **解析时间用了 `now()`**：`parse_unbound`/`parse_dns_log` 忽略日志自带 epoch，重放的历史日志被记成“当前时间”，在 10-29 07:35–07:49、10-30 02:52–03:06 形成 **4434 万行**异常洪峰；
4. **表排序不适合时间查询**：`ORDER BY (type, client_mac, ts)`，按 `ts` 过滤需全表扫描；count + 排序超过 3s 硬顶后，handler 统一返回 `CH_DOWN`“日志存储暂不可达”。

## 修复

### 采集侧

- compose 新增 `vector-data:/var/lib/vector` 持久化 checkpoint；
- 两个 file source 改为 `read_from = "end"`（首次部署只采新日志；需要回填时临时改回）；
- `parse_unbound` 使用日志前缀 `[epoch]`；`parse_dns_log` 使用 JSON `ts`，不再用 `now()`。

### 存储侧

- `logs` 表重建为 `ORDER BY (ts, client_mac, domain)`，与游标排序一致，时间窗查询可顺序扫描；
- 清理两个重放窗口的 4434 万行异常数据（窗口内正常日志约 2–3 万条一并清理，可从日志文件回补）；
- 重建 `logs_topn_hourly` 物化视图；
- 新增 `db/clickhouse/migrations/0001_logs_order_by_ts.sql` 与 `scripts/migrate-ch-logs.sh`。

### 可观测/错误语义

- ClickHouse 超时返回 `QUERY_TIMEOUT`（“查询超时，请缩小时间范围”），不再误报存储宕机；
- 其他存储错误记录服务端日志后返回 `CH_DOWN`。

## 验证

| 时间窗 | 修复前 | 修复后 |
|---|---|---|
| 近 6 小时 | ~2.25s（数据洪峰时 503） | **0.034s** |
| 近 24 小时 | 503 / 3.07s | **0.135s** |
| 近 30 天 | 503 / 5.35s | **0.93s** |

- 行数：67,344,722 → **23,028,604**；
- Vector 重启 20s 增量 895 行（正常速率），无重放；
- `Top` 0.73s、`Qps` 0.11s（30 天窗）；
- E2E 11/11 通过。

## 遗留

- 重放窗口内正常日志已丢失，需要时从 Kea/Unbound 日志文件回填；
- 后续可增加 `ingested_at` 列，用于识别“入库时间异常”的重放数据；
- 首次部署默认不回填历史日志，交付时如需历史需单独操作。
